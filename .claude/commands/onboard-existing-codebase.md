# /onboard-existing-codebase — 既存コードベース導入コマンド

`SETUP.md` の既存コードベース導入パス（Step 1B〜3B）を一気通貫で実行する：実際のスタックを検出し、
`docs/ai-context/*` を逆生成し、`use-cases.md` をas-isでドラフトし、`data-model.md` を抽出し、
すべての検出事項を仕分けたうえで、優先度付きのレビューガイドと、人間向けに明確に分離した2本のリストを
出力して終わる。

> 関連ADR: `meta/adr/ADR-0011-existing-codebase-adoption.md`
> 関連ルール: `.claude/rules/00-global.md`、`docs/development/ai-workflow.md` の「役割分担」

## 実行前に

このパスが正しいか確認する：新規プロジェクトではなく、既にコードが動いている既存プロジェクトであること。
迷う場合は `SETUP.md` のStep 0を参照する。Claude Code組み込みの `/init` は**実行しないこと**——
本テンプレート固有の `CLAUDE.md` を汎用的な形で上書きしてしまう（`SETUP.md` の既存コードベース導入パスにある
「Claude Code組み込みの `/init` はここでは実行しないこと」の注記を参照）。

## 基本原則

動いているコードベースは、現在何が起きているかについての正である。既存の社内ドキュメントは突き合わせ用の
参考資料であり、実際のコードを読むことの代わりにはならない。**曖昧さやコードとドキュメントの食い違いを
推測で解消し、その推測の上にドラフト・実装してはならない。** コードをさらに読めば決着がつくなら決着させ、
その結果を事実として記録する。無害な保守的デフォルトがあるなら（後述のdo-not-touchを参照）それを適用し、
適用したことを明示する。それ以外は「要確認」リストに載せる。本コマンドはあらゆる曖昧さのパターンを事前に
網羅しようとはせず、この一点の手続き上のガードレールに依拠する。

## 手順

### Step 1B — 実際のスタックを検出し、`docs/ai-context/` を逆生成する

1. コード（`composer.json` / `package.json`、マイグレーション、ルート、認証設定）から実際のフロントエンド・
   バックエンドフレームワーク・DBエンジン・認証方式を検出する。`meta/adr/ADR-0001` / `ADR-0002` /
   `ADR-0003` / `ADR-0005` の前提が当然成り立つと決めつけない。
   - テンプレートの前提と一致 → そのまま進める。
   - 不一致（DBエンジンが異なる、認可がPolicy/Gateではなく手書きロールチェック等）→ **要確認**リストに
     named mismatchとして追加する。どちらか一方を黙って書き換えない。
   - バックエンドがそもそもPHP/Laravel系ではない → その場で止め、このテンプレートの既存コードベース
     導入パスがこのコードベースには構造的に合わないと人間に伝える。
   - 検出したフロントエンド/バックエンドのスタックを `/adr` で記録する。Decisionの節には「選んだ」の
     ではなく「検出した」内容を書く。このADRがスタックと認証に関する事実の正式な置き場所であり、
     他のファイルはそれを繰り返し書かずにこのADRを参照する。
   - 不一致が見つかった場合、尋ねるのは開発（`SETUP.md` のStep 4）を始めるのに必要なことだけにする——
     典型的には「この検出結果は正確か？」と「*新規*コードにはどのルールを適用するか？」である。
     スタックを移行するかどうかはオンボーディングの範囲外であり、尋ねないこと。
2. テンプレートのデフォルトスタックを前提としているハーネスファイルを実態に合わせる。そのまま残すと、
   AIが `CLAUDE.md` のタスク表経由でそれらを読み込み、積極的に誤導されてしまう:
   - `docs/architecture/authz-authn.md` — 検出した認証方式がSanctum + Policy/Gateと異なる場合、
     テンプレートの内容をas-isの事実に置き換え、認証の仕組みはスタックADRを参照させる。このファイルは
     それ自体を**P1**のレビュー項目として挙げ、人間には「誰が何をできるか」の部分を見るよう示す——
     ここでの読み違いは、出力全体の中で最も代償の大きい誤りになる。
   - `.claude/rules/15-frontend.md`（フロントエンドがVue 3 + Inertia.js + Piniaと異なる場合）と
     `.claude/rules/20-mysql.md`（DBエンジンがMySQLと異なる場合）— 新規コードがどのルールに従うかは
     人間が判断する事項である。**P1**の「要確認」の質問として追加し、ファイルの先頭に「このファイルは
     このコードベースを記述していない。このファイルが対象とするコードを書く前に人間に確認すること」と
     いう短いバナーを付ける。本文の書き換えは回答を得てから行う。
   - `00-global.md`・`10-laravel.md`・`40-security.md`、および `CLAUDE.md` のグローバルルールには
     決してバナーを付けたり書き換えたりしない。既存コードがそれらの認証ルール（Policy/Gate、Sanctum）に
     従っていない場合はP1の質問にする。人間が回答するまで、それらのルールは新規コードに引き続き適用される。
3. `.claude/hooks/domain-boundary-check.sh --audit-all` を実行する。その指摘は**Backlog**リストに
   載せる——「要確認」リストには載せない（`meta/adr/ADR-0010-domain-boundary-contract.md` の
   「積み残しであってブロッカーではない」という考え方を参照）。
4. 実際にそこにあるものから `docs/ai-context/project-summary.md`・`module-map.md`・`glossary.md`・
   `common-commands.md`・`do-not-touch.md` をドラフトする。短く保つこと（`.claude/rules/60-docs.md`:
   ai-contextは要約レイヤーである）——詳細をコピーせず、要約して正式なファイルへリンクする
   （`project-summary.md` は毎セッション読まれるため、スタックの1行要約は残す）。業務上の意味の推測には
   すべてインラインで **[inferred]** を付ける。「要確認」リストに載るのはそれらだけであり、機械的に
   読み取れる内容（ディレクトリ構成、`composer.json`/`package.json` の実際のコマンド）はどちらの
   リストにも載らない。
   - 不確かなdo-not-touch境界については、尋ねる代わりに保守的デフォルト（do-not-touchとして扱う）を
     適用し、レビューガイドの「適用したデフォルト」に記載する——人間は後から緩めることができ、それまでの間
     慎重すぎる境界が害を生むことはない。
5. このプロジェクトを記述しているものとして読まれる、その他のテンプレートファイルを埋める:
   - `CLAUDE.md` の **Project** 節（毎セッション読み込まれる）: プロジェクト名、スタック（1行で書き、
     スタックADRを参照させる）、種別は機械的に書ける。**Main domains** は業務上の意味の推測なので
     **[inferred]** を付け、P2とする。
   - `docs/product/org-permission-philosophy.md`（認可を変更するたびに読まれる）: コードに存在する
     ロールを列挙する。各ロールの目的と対象ユーザーは **[inferred]** とし、P2とする。
   - `docs/product/ui-guidelines.md`（UIの作業のたびに読まれる）: 既存のスタイル・テーマ設定が実際に
     定義しているものだけを書く。何も定義されていなければ、プレースホルダーを「定義なし。新しい画面は
     既存の画面に合わせる」という1行に置き換える。

### Step 2B — 現状の挙動を `use-cases.md` として文書化する（as-isであり理想形ではない）

1. 実際のコードパス（routes → controllers → policies）から `docs/product/use-cases.md` をドラフト
   する。これは現状の挙動の記述であり、望ましい挙動の仕様ではないと明記する。ルートを通らない入口——
   コンソールコマンド、スケジュール実行のタスク、キューのジョブ、イベントリスナー——もたどること。
   ここで漏れたものは、誰にも気づかれないまま漏れる。Step 1Bと同様に、業務上の意味の推測には
   **[inferred]** を付ける。
2. `docs/product/requirements.md` は任意——「まだ存在しないものをなぜ作るか」という本来の目的が、
   既に動いているコードには当てはまらない。ただしテンプレートのプレースホルダーをそのまま残さないこと：
   このプロジェクトは既存コードベース導入パスでオンボーディングされたこと、挙動の参照先は
   `use-cases.md` であること（レビュー不要）を記した1行の注記に置き換える。
3. コードが既存の社内ドキュメント（例: `docs/original-docs/`）と食い違う場合は、「要確認」リストに
   食い違いメモを追加する。どちらか一方を黙って解消してはならない——`.claude/rules/00-global.md` の
   「ユーザー向け挙動変更には常に承認が必要」を参照。
4. `bash .claude/hooks/spec-lint.sh` を実行し、構造上の指摘（ID、欠けているセクション、テンプレートの
   残り文言）をすべて修正する。未解消の **[inferred]** マーカーは残してよい——それらは「要確認」リストで
   決着させる。

### Step 3B — 実スキーマから `data-model.md` を抽出する

1. 実際のマイグレーション・DBスキーマから `docs/architecture/data-model.md` を生成する。ほぼ完全に
   機械的な抽出作業であるため「要確認」リストに載ることは稀であり、Step 1Bで確認したDBエンジンが
   前提となる。
2. `docs/architecture/overview.md` のテンプレート内容を、as-isのシステムコンテキストに置き換える：
   コンポーネント、すべてのDB接続、外部API、フロントエンドの配信方法。これは機械的な作業である——
   図1つとコンポーネント表1つにとどめ、詳細はスタックADRを参照させる。

### 仕分け — 何かを出力する前に、すべての候補項目を仕分ける

出力の目的は、人間のレビュー負荷を最小にすることである：人間に尋ねるのは、コードからは答えが出ないこと
（業務上の意味と意図）だけにする。Step 1B〜3Bで集めたすべての項目を、次のいずれか1つのバケットに仕分ける:

| バケット | 判定基準 | 行き先 |
|---|---|---|
| 機械的な事実 | コード・設定・スキーマから直接読み取れる | ドラフトしたドキュメントのみ——リスト項目には決してしない |
| AIで検証可能 | コードをさらに読む、grepする、または実DBや外部サービスに触れない読み取り専用コマンドを実行すれば決着がつく（例:「このクラスは解決できるか？」「このルートは参照されているか？」） | その場で検証し、結果を事実として記録する。人間には尋ねない |
| コードの欠陥 | コード自体の問題（インジェクションになりうるSQL、デッドコード、安全でないHTTPメソッド、誤ったステータスコード、ドメイン境界違反）——どちらにせよドキュメントはそれを正確に記述している | **Backlog**。ユーザーが観測できるもの（例: 誤ったステータスコード）は、質問としてではなくas-isの挙動として `use-cases.md` にも記録する |
| 人間の判断が必要 | 業務上の意味、意図、またはどのルールを適用するかの判断——コードから導けない、またはAIが使ってはならないアクセス（例: 本番DB）が必要 | **要確認** |

各事実は正式なファイル（スタック・認証の事実 → スタックADR）に一度だけ書き、他のファイルからは繰り返さずに
そこを参照する——重複は1つ増えるごとにレビュー箇所が1つ増える。

## 出力形式

以下の3つのセクションをこの順序で出力する。ユーザーとの会話の言語で書くこと。

### 1. レビューガイド（最初に出力する）

人間がどこから始めればよいかを示す入口。一目で追える形に保つ。

1. **生成したもの** — 作成・変更したすべてのファイルの表。*新規* / *テンプレートを置換* / *一部編集* の
   区別と、内容の1行要約を付ける。
2. **レビュー順** — 「要確認」項目を含むファイルと、置き換えた `authz-authn.md` を、次の順に並べる:
   - **P1** — どのルールを適用するかを変える、または他のドキュメントを無効にしうる事実・判断（例:
     スタックADR、置き換えた `authz-authn.md`、認証がないのは意図的か、どのフロントエンドルールを
     適用するか）。他の回答がこれらに依存するため、最初に回答する。
   - **P2** — 業務上の意味の推測を含むドキュメント（例: `use-cases.md`、`glossary.md`、`CLAUDE.md` の
     Main domains、`org-permission-philosophy.md`）。
   - **P3** — 機械的に抽出したドキュメントのうち、局所的な異常があるもの（例: マイグレーション欠落の
     食い違いが1件ある `data-model.md`）。

   各ファイルについて、*何を見るか*（具体的な節や項目）と、セクション2の*どの質問番号*に関係するかを
   示す——「ファイル全体をレビューしてください」とは決して書かない。
3. **適用したデフォルト** — AIが尋ねる代わりに選んだ保守的デフォルト（例: 不確かなdo-not-touch境界）。
   人間が対応するのは、それが誤っている場合だけである。
4. **レビュー不要** — 純粋に機械的な抽出、またはas-isの事実に置き換えたファイル（例: `module-map.md`、
   `common-commands.md`、`overview.md`、`requirements.md`、`ui-guidelines.md`）を列挙し、人間が明示的に
   飛ばす・流し読みできるようにする。**[inferred]** マーカーや「要確認」項目が1つでもあるファイルは、
   ここに挙げた例に当たるものでも、決してここに入れない。

### 2. 要確認（ブロッキング）

人間とこのリストを解消することが、そのままGate 0〜3の承認になる。

- すべての項目に番号を振り、1行で答えられる質問の形にする（yes/no、選択肢、または短い定義）。
  優先度（P1〜P3）と、その回答で更新されるファイルをタグとして付ける。
- 優先度順、次に依存関係順に並べる（他の質問を変えてしまう回答が先）。
- 用語集の用語、`CLAUDE.md` の Main domains、`org-permission-philosophy.md` の各ロールの目的は、
  記入用の表付きの1つの質問にまとめて尋ねる。それでもリストが10項目程度を超える場合は、他の関連項目も
  同じようにまとめ、個別に並べない。
- 人間はチャットで質問番号を指定して回答できること、ドキュメントを更新するのは人間ではなくAIであることを
  伝える。

### 3. Backlog（非ブロッキング、任意）

既存コードの欠陥：`domain-boundary-check.sh --audit-all` の指摘と、仕分けの「コードの欠陥」バケット。
セキュリティ関連の項目を先に並べる。このリストは参考情報であり必須事項ではないことを明記する。
どの項目が自然に再浮上し、どの項目が再浮上しないかを伝える：ドメイン境界の指摘は今後の `/review` の
たびに再浮上するが、それ以外のコードの欠陥は今回一度しか表示されないため、残しておきたいものは人間が
記録する（例: 課題管理ツールに登録する）。また、`SETUP.md` Step 4 の初回のみのテスト設定
（`Model::shouldBeStrict`、`DB::prohibitDestructiveCommands`、`Http::preventStrayRequests()`、SQLiteではなくMySQLでのテスト実行）が
未導入であれば、それも列挙する：既存テストが失敗したりステージング環境で例外が発生したりしうるため、
有効にするかどうかは人間が判断する。

最後に、人間に対して明示的に念を押す：**開発に入る前に人間によるレビューが必要である**——「要確認」の
質問に回答すること（これがGate 0〜3の承認になる）、そしてそれらが解消されるまで `/tdd` を始めては
ならないこと。その後は止まって待つ。実装作業には一切進まないこと。

## 人間が回答した後

1. 各回答を、その質問にタグ付けされたファイルに反映する。解消済みの **[inferred]** マーカーと
   「要確認」の注記を取り除く。
2. 回答から新たな質問が生じた場合は、推測せずに尋ねる。
3. すべての項目が解消したら、`bash .claude/hooks/spec-lint.sh` を再実行し、残っている指摘
   （例: 取り残された **[inferred]** マーカー）があれば承認依頼と一緒に示す。
   そのうえで人間に明示的な承認を求める。承認を得た後にのみ、それを
   `docs/product/use-cases.md` の承認記録（レビュアーは人間）と `PLAN.md` に記録する。この1回の承認が
   Gate 0〜3を満たす。すべて解消したという自分の判断だけで記録してはならない。

## 制約

- スタック不一致・業務上の意味の推測・コードとドキュメントの食い違いを、コードで検証するか尋ねるかせずに
  確定事項として扱ってはならない——上記「基本原則」を参照。
- Backlogリストを新規ファイルとして永続化しない。チャット出力のみとする（理由は
  `meta/adr/ADR-0011-existing-codebase-adoption.md` を参照）。
- 組み込みスキル `security-review` を本コマンドの一部として実行しない——diffのみのスコープであり、
  引き継いだアプリケーションコードをカバーできない（`meta/adr/ADR-0011-existing-codebase-adoption.md`
  を参照）。

## 使用例

```
/onboard-existing-codebase
```

→ 上記の手順を実行し、「出力形式」の3つのセクションを出力する。
