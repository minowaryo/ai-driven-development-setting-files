# traceability-matrix.md — トレーサビリティマトリクス

> 要件ID ↔ ユースケース ↔ コード ↔ テスト の対応関係を管理します。
> 変更管理・影響分析・監査対応に使用します。
> このテーブルは、下記の変更追跡エントリに合わせて手動更新する運用と、定期的に一括再生成する運用（後述の **Maintenance** 参照）のどちらでも構いません。プロジェクトでのRCID発行頻度に合わせて選んでください。

## RCID命名規則

```
CHG-[連番4桁]
例: CHG-0001, CHG-0042
```

## ステータス定義

| ステータス | 意味 |
|---|---|
| Complete | 実装ファイルと、実際の挙動を検証するFeature/Unitテスト（Policy/認可のみのテストは含まない）の両方が確認できた |
| Partial | 実装は存在するが、テストが未整備・間接的、または認可チェックのみにとどまる |
| Not Found | 実装・テストのいずれも見つからなかった — 未実装の可能性が高いとみなし、このテーブルに頼る前に確認すること |

## 使い方

1. 新機能追加時: 要件IDとUCIDを先に決めてからコード生成を依頼する
2. バグ修正時: 関連する要件IDを特定してトレーサビリティを維持する
3. 変更管理: RCID を発行してコードと要件の変更を紐づける。定期的な再生成でテーブルを最新化する運用の場合は、個別の行を手で直すのではなく、下記Maintenanceの手順で作り直す

## Maintenance（再生成方式 — コミット単位の手動更新ではない場合）

コミットのたびに手動更新するのではなく（コミット単位の追随は、このようなテーブルを陳腐化させる原因になりがちです）、定期的に（例: `/review` 実行時やリリース前に）一括再生成する運用を選んだプロジェクトの場合の手順:

1. `docs/product/use-cases.md` の `### UC-XXX` 見出しと、その直後の `**Related requirement**` 行から UC ID → タイトル → 要件ID を抽出する。
2. 各UCについて、リソース名での検索によりアプリコード側の実装ファイル・テストスイート側のテストファイルを特定する（名前だけで一致が曖昧な場合のみファイル内容を確認する）。
3. 上記のステータス定義に従ってStatusを記入し、対応するUCが存在しない要件IDがあれば書き添える。
