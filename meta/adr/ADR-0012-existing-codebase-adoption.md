# ADR-0012: 既存コードベースへの導入パス（Gate 0〜3）

## Status
Accepted

## Date
2026-09-15

## Context

`meta/adr/ADR-0004-ai-development-policy.md` のワークフロー図は **グリーンフィールド**（新規開発）プロジェクトを前提としている——コードが一切存在しない段階で、人間が白紙から `requirements.md` を書き、次に `use-cases.md`、次に `data-model.md` を書く、という順序である。本ハーネスには、その逆のケース——**すでに動いているコードが存在する**プロジェクトへの導入（開発途中からの参加、レガシーの引き継ぎ、既存アプリへの本ハーネス導入）——に対応する記述が存在しなかった。このケースでは:

- 「何を作るか、まだ決まっていない」という段階自体が存在しない——コードはすでに何らかの意思決定を体現しており、その意思決定は文書化されていないか、既存の社内ドキュメントから乖離している可能性がある。
- Gate 0で本来行うべき作業が反転する。「人間が `docs/ai-context/*` と `use-cases.md` を白紙から書く」のではなく、「AIが実際のコードを読んでそれらを叩き台として生成し、人間が実システムと突き合わせて検証する」という形になる。
- 現在何が起きているかについては、既存の社内ドキュメントではなく**動いているコードの方が正**である——逆生成した `use-cases.md` は、コードと旧ドキュメントの食い違いを発見事項として記録するべきであり、どちらか一方を黙って正としてはならない。これは新しいルールではない。`.claude/rules/00-global.md` の「ユーザー向け挙動変更には常に承認が必要」は、プロジェクトのどの段階であっても、仕様と実装の食い違いは報告すべき発見事項であり行動の指令ではない、と既に定めている。本ADRはこの既存ルールを特定のドラフト作業に適用しているのであり、競合する新ルールを導入するものではない。
- 本ハーネス自身が固定している技術スタックの前提（`ADR-0001` Laravel、`ADR-0002` MySQL、`ADR-0003` Sanctum + Policy/Gate）は、本テンプレートから新規に作られたプロジェクトに対しては当然成り立つが、既存コードベースに対してそうであるとは限らない。現状「プロジェクトごとに検出・選択する」扱いになっているのはフロントエンド（`ADR-0005`）だけであり、バックエンドフレームワーク・DBエンジン・認証方式についてはそのような扱いがなく、既存コードはこれら3点のいずれからも容易に乖離しうる。
- 人間のレビュー時間こそが本ハーネスが一貫して守ろうとしているボトルネックである（`ADR-0009` の `review-score` によるレビュー強度の自動判定、`ADR-0011` の指摘優先度シグナルを参照）。AIが逆生成したものを人間がすべて再検証しなければならない設計では、ドラフト作業を自動化した意味が失われる。

## Decision

### 1. Gate 0内での分岐であり、フォーク（別リポジトリ・別ファイル）ではない

`SETUP.md` に「Step 0 — 導入タイプの判定」を、既存のStep 1の前に追加する。新規プロジェクトは従来通りStep 1〜4に進む。既にコードが存在するプロジェクトは、新設する「既存コードベース導入パス」（Step 1B〜3B）に進み、その後は既存のStep 4（TDD: Red → Gate 4 → Green → Refactor、両パスで共通）に合流する。これは `ADR-0005` が既に採用している「Gate 0の内部で分岐する」というパターンをそのまま踏襲したものである——Gate 1〜4の仕組みおよび `.claude/rules/10〜60` はどちらのパスでも同一であり、異なるのはGate 0〜3の**入力**がどう作られるかだけである。

用語について: 本リポジトリでは既に `ADR-0011` の中で、まさにこの状況を指して「ブラウンフィールド」という語を1回使っている。新設する見出しでは平易な説明（「既存コードベース導入パス」）を主とし、「（ブラウンフィールド導入）」を括弧書きで併記するにとどめ、競合する用語を新たに持ち込まない。

### 2. スタック検出を、フロントエンドだけでなく全体に一般化する

Step 1Bでは、フロントエンドだけでなくバックエンドフレームワーク・DBエンジン・認証方式も実際のコードから検出する——`ADR-0005` がフロントエンドに対してのみ行っている「検出する、決めつけない」という扱いを全体に広げたものである。`ADR-0001`/`ADR-0002`/`ADR-0003` との不一致（DBエンジンが異なる、認可がPolicy/Gateではなく手書きロールチェックである等）は「要確認」リストに named mismatch として記録し、どちらか一方を黙って書き換えることはしない。**根本的な**不一致（バックエンドがそもそもPHP/Laravel系ではない）の場合は、その場で作業を止めてユーザーに伝える——このパスがそのコードベースに構造的に合わないということであり、Laravel向けのルールを無理に適用することはむしろ有害な誤誘導になる。

### 3. 出力リストは2本立て——ブロックするのは片方のみ

- **「要確認」リスト（ブロッキング）** — 逆生成した**ドキュメント自体**の信頼性に関わるものだけ：用語の意味の推測、do-not-touch境界の推測、use-casesの食い違い、ルール適用先を左右するレベルのスタック不一致。このリストを解消することが、そのままGate 0〜3の承認になる——Step 1B〜3Bは `docs/ai-context/*`・スタックADR・`use-cases.md`・`data-model.md` を1回のドラフト作業でまとめて生成するため、これらを（新規開発のようにドキュメントが数週間おきに届く前提の）4回の個別承認としてゲートするのは形式的な儀礼にすぎない。
- **「Backlog」リスト（非ブロッキング、提案のみ）** — ドキュメントではなく**コード自体**に既に存在する問題：`.claude/hooks/domain-boundary-check.sh --audit-all` の指摘（Controllerでの直接DBアクセス、インラインロールチェック等）。「要確認」リストと並べて提示するが、「先に進む前に必須」とは明記しない。これは `ADR-0011` 自身が既に述べている「ブラウンフィールドへの導入は積み残しを可視化するのであって、ブロッカーにはならない」という考え方をそのまま具体化したものである——本決定の初期ドラフトではBacklogの指摘をブロッキング側のリストに混ぜてしまっており、これは `ADR-0011` の立場と矛盾していたためレビューで修正した。
- **Backlogリスト用の専用ファイル・ディレクトリは持たない。** チャット出力のみであり、現在の `/review` の指摘表示と同じ扱いとする。`domain-boundary-check.sh` は `ADR-0011` により今後の `/review` のたびに同じ指摘を再導出するため、保存したスナップショットはすぐに陳腐化する重複コピーにしかならない。
- **組み込みスキル `security-review` は意図的にオンボーディングへ組み込まない。** このスキル自体のスコープは「現在のブランチの変更内容（pending changes）」——`/review` と同じくdiffスコープ——であり、whole-tree走査用に `--audit-all` を専用に持つ `domain-boundary-check.sh` とは異なる。オンボーディング自体が生成する差分はドキュメントのみであり、そのdiffに対してdiffスコープのセキュリティレビューを実行しても、引き継いだアプリケーションコードは一切見えず、誤った安心感を与えるだけになる。`security-review` は今まで通り、実際にコードを触る将来のPRで人間の判断により任意実行する汎用ツールのままとし、このパスが自動化したり特別扱いしたりする対象には含めない。

### 4. 確信度に応じたドラフト作成

すべてのドラフトは、「機械的に抽出した内容」（コード・設定から逐語的に読んだもの——即座にAIの参照情報として使え、人間のチェックを必要としない）と、「推測・判断を要する内容」（用語の意味の推測、do-not-touch境界の推測、スタック不一致、use-casesの食い違い）を明確に区別する。後者だけが「要確認」リストに載り、既存コード自体の問題は上記の区分に従ってBacklogリストに載る。

### 5. 人間とAIの役割分担を明示する

`docs/development/ai-workflow.md` の「役割分担」は、新規プロジェクトと既存コードベース導入の両方を並べて示すようにし、後付けの注記にはしない。両者で共通するのは「AIがドラフト・生成し、人間が判断・承認する」「人間の承認前にAIが実装コードを生成することはない」「最終レビュー・マージは常に人間」という全体構造であり、異なるのは**人間が何について判断するか**である。新規開発では人間の役割は「白紙から著述すること」、既存コードベース導入では「AIがドラフトした内容を実システムと突き合わせて検証・判断すること」である。

### 6. 分岐の開始は一部自動化されている

`.claude/rules/00-global.md` は `CLAUDE.md` の「毎セッション読み込みリスト」には含まれておらず、関連するとき（例: `/review` 実行時）にのみ参照される。そのため、検出のためのチェックをそこだけに置いても、「ログイン機能を追加して」のような何気ない最初のプロンプトでは発火しない。毎セッション最初に必ず読まれることが保証されている唯一のファイルは `docs/ai-context/project-summary.md` である（このファイル自身がそう明記しており、`CLAUDE.md` の「毎セッション読み込みリスト」の1行目でもある）。そのためトリップワイヤーはこのファイルのプレースホルダー本文に持たせる：プレースホルダーが残ったままで、かつリポジトリに既に実質的なアプリケーションコードが存在する場合、他の依頼に着手する前に既存コードベース導入の可能性を提案する。`.claude/rules/00-global.md` 側には補助的なチェックとして同じ内容を残すが、これは補強であって主たるトリップワイヤーではない。

### 7. 新設するスラッシュコマンド——`/init` の拡張版という位置づけ

`.claude/commands/onboard-existing-codebase.md` を、`/generate-mock` / `/adr` / `/tdd` / `/review` と同じ形式で新設し、Step 1B〜3Bを一気通貫で実行して上記2本のリストを出力する。Claude Code組み込みの `/init` をこのテンプレートに対して実行することは推奨しない——`/init` はコードベースを走査して単一の汎用的な `CLAUDE.md` を（上書き）生成するものであり、本テンプレート固有の `CLAUDE.md`（Gate 0案内、「毎セッション読み込みリスト」等）を、それを知らない汎用的な形で潰してしまう。`/onboard-existing-codebase` は、同じ発想を本ハーネス向けに拡張・専用化したものと理解するのが適切である——単一の汎用`CLAUDE.md`ではなく本ハーネス固有のファイル形（`docs/ai-context/`の5点セット）を対象とし、汎用的な要約ではなくバックエンド/DB/認証のスタック検出を追加し、`domain-boundary-check.sh` と連携し、`/init` が一切踏み込まない `use-cases.md`（as-is挙動）と `data-model.md` の生成にまで踏み込む。

### 8. あえてルールブックにはしない

本決定は、コードとドキュメントの食い違いのあらゆるパターンを事前に網羅しようとするものではない——そのようなことをしても、結局は都度ユーザーと個別に検討し直すことになり、初期セットアップを不必要に重くするだけである。確実に守るべき一点だけがある：手続き上、曖昧さを推測で解消して先に進んではならない——「要確認」リストに載せて必ず尋ねる。この単一のガードレールこそが、AIが「コードの方が正しい」（あるいは「ドキュメントの方が正しい」）と黙って決めつけてその推測のままドラフト・実装してしまうという、本当に防ぐべき失敗モードを防ぐものであり、ケースの網羅性を追求することではない。

## Rationale

- `ADR-0005` の「Gate 0内部で分岐する」という前例を、フロントエンドのみから全体に一般化した。
- `ADR-0009`（`review-score`）の「一律の強度で見るのではなく、必要なところに人間の労力を振り向ける」という前例——確信度に応じたドラフト作成、統合された1回の承認、ブロッキング/非ブロッキングのリスト分割は、いずれもこの同じ原則をドラフト作成・Gate構造・指摘のトリアージに適用したものである。
- `ADR-0011` 自身の「ブラウンフィールドへの導入は積み残しを可視化するのであって、ブロッカーにはならない」という枠組みが、`domain-boundary-check.sh` の指摘をブロッキング側から外す直接の前例である。

### 採用しなかった代替案

- **既存コードベース導入専用の別リポジトリ・別テンプレートを用意する**: 不採用。Gate 1〜4の仕組みおよび `.claude/rules/10〜60` はどちらのパスでも同一であり、フォークすればコンテンツの9割が重複し、今後のテンプレート更新のたびに乖離が生じる。
- **このパスでもGate 0〜3を4回の個別承認のまま維持する**: 不採用。新規開発ではドキュメントが数週間おきに届くため4回の承認が自然だが、既存コードベース導入では4つの成果物が1回のドラフト作業でまとめて届くため、形式的な儀礼になる。
- **Backlogの指摘をブロッキングの「要確認」リストに混ぜる**: 本決定の初期ドラフトではこうしていたが、レビューで不採用とした——既存コードの構造的・セキュリティ的な負債が、無関係な作業を止める計画外のブロッカーになってしまうため。
- **組み込みスキル `security-review` をオンボーディングに組み込む**: 不採用——diffのみを見るスコープのため、オンボーディングのドキュメントのみの差分をレビューすることになり、引き継いだアプリケーションコードは見えないまま、本来意図した仕事をせずに「カバーした気になる」だけに終わる。
- **Backlogリストをファイルとして永続化する**: 不採用——`domain-boundary-check.sh` が今後の `/review` のたびに同一の指摘を再導出するため、保存したコピーは陳腐化するだけである。

## Consequences

### メリット

- 既存プロジェクトが、暗黙のアドホックな運用ではなく、文書化された汎用的な導入経路を得られる。
- 人間のレビュー時間が実際の不確実性に比例する：小規模で理解しやすいコードベースなら「要確認」リストは短く承認も速い。大規模・曖昧なコードベースならリストは長くなるが、機械的に検証可能な内容を丸ごと再レビューさせられることはない。
- Gate 0〜3の条件表（`.claude/rules/00-global.md`、`AGENTS.md`）は一行のポインタを追加するだけで済み、手順そのものの書き換えは不要なので、今後の変更は `SETUP.md` の1箇所に集約される。

### デメリット・リスク

- AIが逆生成した「as-is」ドキュメントが誤っている可能性はある——これはGate 0〜3の条件そのものに「フラグを人間が解消すること」を組み込むことで緩和しており、任意のおまけレビューにはしていない。
- PHP/Laravel系ではないコードベースには「構造的に合わない」と正直に伝える——これは後で直すべき欠陥ではなく、意図した正しい挙動として扱う。
- Backlogリストを永続化しないため、オンボーディング時点でそれを無視した人間は、次に `/review` を実行するまでローカルな記録を持たない——`/review` はマージ前に必ず実行される既存の運用があるため、許容できるトレードオフとする。
